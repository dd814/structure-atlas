# 复杂结构图谱

先让读者看懂整体如何协作，再让他们追到一个具体部件和它的证据。默认用对非专业读者友好的语言，保留可查证的文件名、术语和行号。

1. 从用户最想弄懂的问题或一个具体场景出发。查看可用的源码、文件、文档或业务记录，找出入口、输出、主要中间交接和例外。以证据判断现状，区分已运行、实验、计划和推测。保留关系的依据。
2. 首页放关系总图。挑出能解释全局的核心节点。把箭头标明方向和交接内容，例如请求、返回、调用、数据、约束或依赖。把支线接到它真正进入的节点。并行分支、反馈回路、跨层依赖和人工触发，应画出各自的关系。只有先后关系时，不把它画成调用或因果。
3. 用一条具体流程带读者走过总图，注明每步谁接手、输入如何变成下一步的东西、结果去哪里。如果组织方式没有时间顺序，就用一个具体问题展示如何沿关系找到答案。整体图和流程可以是同一页，也可以切换阅读。
4. 有详细阅读需求时，做可展开的部件页。每个部件先给一句职责，再显示上游、下游、协作方式和直接跳转。源码地图按用户要求覆盖文件与有意义的代码块，长函数可分段。注明行号和出处，提供可选源码展开。微小实现细节放在深一层，不挤占总览。
5. 检查不同箭头是否可区分，是否有无意断开的核心节点，窄屏是否可读，点击是否到达正确内容。抽查关键关系的证据。把范围和缺失证据写清楚。用户之前反馈“连成一片”时，优先修正节点留白、关系线、总览与细节的分离。

简单结构可直接用 Mermaid。分支多、需要跟着数据走或需要从总图钻到源码时，优先提供可交互阅读的图谱。做单文件离线 HTML 时，阅读 [模板数据格式](references/html-template.md)，用 [生成脚本](scripts/build_atlas.py) 复用自带模板。只按用户要求保存到指定位置或发布。
